## OP-03 — Root-confirmed Admin fulfillment (2026-10-17)

- Admin Bot gains «🔌 فعال‌سازی اشتراک‌ها» and `/fulfillment`: trusted, linked, private Super Admin views only paid managed-plan orders with existing `sales_fulfillment_outbox` intent. Selection and 3-minute, per-root one-time confirmation enqueue a **single-order Laravel Job**. No provider request happens inside Telegram Webhook. Job implements unique order key, one attempt, bounded runtime and logs only generic outcome with order id.
- Actual provider POST uses **unchanged** `FulfillPaidPlanOrder` settlement journal verification, Plan revision/Squad checks, unique durable create reservation, terminal `needs_review` on uncertain writes and protected order-to-subscription mapping. Queue duplicates cannot cause a second POST. An ambiguous order offers separate root-confirmed **GET-only reconciliation**, reusing `FulfillPaidPlanOrder::reconcile`, with no blind create retry.
- When provider writes or globally verified Squad gate are OFF, activation action is unavailable. No finance enablement, user/client signup, automatic bank settlement, automatic paid-event fulfillment, Node/Host provisioning, new migration, provider flag or root role changes. Source CI and isolated fake-provider tests cannot prove real customer VPN connectivity; live two-bot/Remnawave/bank tests remain deferred together until after OP-03 by operator request.

**Approved:** 2026-10-17. Six independent phases. This is the approved Sales development scope, not authorization to turn on public accounts, banking, provisioning or customer cutover.

## Boundaries and delivery rules

- Exactly two Telegram bot identities, one Laravel application, shared Identity, Sales, Billing and Provisioning Application Actions, one primary database.
- Preserve the original Admin bot's supported Member/Reseller operations until a separate controlled cutover. The Sales router must never import Admin handlers or legacy Sales routes.
- Each phase: smallest PR, focused Pest regression, PHP 8.4/8.5 and disposable MySQL CI, PHPStan, Pint, review and merge to master; update only necessary docs.
- Production activation stays separate: Sales runtime, public signup, Telegram notifications, money and Remnawave writes all remain OFF until their explicitly approved gates. GitHub merge auto-deploys; source CI is not real Telegram/bank/provider E2E.

## SB-05 — Paid-plan provisioning source and safety checkpoint (2026-10-17)

- Internal single-order `FulfillPaidPlanOrder` consumes the **existing** `sales_fulfillment_outbox` and `RemnawaveSubscriptionLifecycle`. It is **not** invoked by Telegram, a bank review callback, a queued job or the scheduler. One explicit `sales:fulfillment:run {order}` operator command is available for separately approved isolated staging checks only.
- Before any POST, require `REMNAWAVE_WRITES_ENABLED=true` **and** `REMNAWAVE_SQUAD_BINDINGS_LIVE_VERIFIED=true`, a `paid` SB-03 plan order with a complete immutable snapshot, the same currently verified Plan–Squad UUID, and a real settlement from the existing bank/wallet Billing journal with matching amounts and postings. Historical F09 orders, unpaid/forged paid orders and invalid/mismatched bindings fail closed.
- Reserve one `processing` outbox intent in the database transaction **before** the provider write. The existing lifecycle reserves exactly one `provisioning_subscriptions` reference (`sales-order:{id}`) and immutable create operation key, validates remote username/ownership marker, quota/expiry/status/squad, and never repeats an uncertain create. On success, uniquely bind the order to that subscription, mark order `fulfilled` and outbox `completed` in one local transaction; existing owner-scoped subscription read actions remain the only customer access.
- On a network/response/local completion uncertainty, hold outbox `needs_review` (and lifecycle `needs_review` when reserved). No retry or implicit consumer. The explicit `--reconcile` command performs **only a remote GET** via the existing lifecycle, requiring matching ownership marker and all persisted creation expectations before locally completing the order; an absent/mismatched remote user remains blocked. Reconciliation never posts another user.
- Time/unlimited plans map `traffic_gb=NULL` to Remnawave's unlimited quota `0`; volume/hybrid snapshots use exact GiB-to-byte multiplication, `NO_RESET`, and an absolute UTC expiration from the single write attempt. No renewal, refund, server/Node creation, subscription-link UI or configuration/flag migration.
- Outbox `needs_review` becomes visible as an aggregate (no IDs/PII) via `php artisan telegram:ops:status`. Buyer order detail acknowledges the `fulfilled` state but does not expose provider secrets. The actual subscription screen is SB-06.
- **Safety/operations:** This is source preparation, not authorization to enable provider writes or purchase/banking in Production. The user's 2026-10-17 private Sales Bot /start/menu smoke reached 17 processed updates and 1 positively linked Sales contact; this does **not** validate payment, a real Remnawave POST/GET, a Node/Host, or a customer connection. The operator previously observed SB-03 migration pending; Production migration must be checked before any checkout test. Always preserve `REMNAWAVE_WRITES_ENABLED=false` on Production. Rollback via code/flag only; existing accounting/provisioning records must never be dropped.
- **Acceptance boundary:** Pest/HTTP fake, isolated SQL, PHP 8.4/8.5, MySQL CI, PHPStan/Pint separately from real staging. No source CI test is equivalent to the approved real-provider staging and live two-bot, bank and end-to-end checks.

Admin can always inspect the durable `/payments` queue; real cross-bot notification rollout is a separate approval gate.
- For an explicitly enabled non-public two-bot environment, an active root receives Sales-origin receipt media only through the Admin token (or safe identifier fallback) and an active Sales buyer with a positively reachable Sales contact receives the decision from the Sales token. No copied provider credentials, unbounded media, direct bot-to-bot IDs, or message forwarding hacks.
