## CFG-02 — Controlled Config Profile lifecycle (2026-10-17)

- **MVP scope:** Private trusted Super Admin Admin Bot creates a named **base-only** Config Profile using a fixed minimal, non-listening Xray config: `{log:{loglevel:warning}, inbounds:[], outbounds:[{tag:DIRECT,protocol:freedom}]}`. It deliberately contains **zero inbound listeners, user accounts and cryptographic secrets**, and is not automatically linked to any Node or Host; operator must configure real Inbounds in the trusted Remnawave panel before use. Other actions: safe **rename only** (PATCH UUID+name; no raw Xray edits) and deletion with proof of **zero Node and Host dependencies**. Existing CFG-01 browsing preserved. No general-purpose JSON editor, private key duplication, inbound mutation, complex preset library, default selection or production provider writes.
- **Controls:** Existing `REMNAWAVE_WRITES_ENABLED` stays default OFF. One 10-minute root-bound confirmation ticket is consumed before any provider POST/PATCH/DELETE; no automatic retry of ambiguous remote outcomes. Root authorization and the write flag checked again under `profiles:mutation` lock. Create requires a unique 1–64 character safe name. Rename re-reads the current profile identity and blocks unchanged names. Delete holds existing `nodes:mutation` and `hosts:mutation` locks while it rechecks latest profile identity, CFG-01 Node associations (must be explicitly verified empty), and **every Host** association (no linked or unknown binding permitted); any incomplete, failed, stale or ambiguous data blocks deletion. This protects in-app races but cannot make external panel writes atomic.
- **UX:** Admin `cfg2:begin/prepare/apply/cancel` links from Profile list/detail; input is name-only, with one-shot preview, copy-safe bounded names, return/cancel and clear warnings for incomplete base profiles and destructive deletes. Conflicting Node/Host text drafts are retired on new wizard starts and vice versa. No Sales route, database schema, new dependency, config flag or CI workflow alteration.
- **Acceptance:** Fake-HTTP tests verify endpoint methods and exact payload allowlist, disabled writes, root/private-only routes, name/UUID validation, no duplicate submits after 504, rename preserving config, deletion blocked by linked/unknown Nodes/Hosts and stale profiles. Pre-merge CI requires PHP 8.4/8.5 + PHPStan/Pint + MySQL. **Actual Remnawave v3.4.4 acceptance of the fixed empty-Inbound template, live Telegram UI and production effects remain unverified** and must not be asserted as tested. No real Provider write is issued by this work.

The ticket is atomically consumed **before** an outbound mutation and cannot be replayed or automatically retried after uncertain remote outcomes. Every operation checks RBAC and existing **default-OFF** `REMNAWAVE_WRITES_ENABLED` both before preparing and immediately prior to the provider request. Stale Node/Host free-text wizards are retired when a competing wizard begins.
- Evidence/limitations: fake Remnawave HTTP, Nutgram and isolated Admin/Sales router tests cover PATCH/POST/DELETE contract, permissions, write gate, stale state, disabled-before-delete, selection across pages, single and batch one-use behavior, 504 uncertainty, and preservation of HOST-01 functionality. No production toggles, migrations, dependencies or provider requests were authorized.

## F09-A acceptance criteria
- Products/rates are small, operator-managed DB records, not guessed tariffs or user-editable pricing. No HTTP or Telegram write endpoint.
- Active customers can read available products and request a **read-only** quote. Inactive/nonexistent buyers are denied.
- Volume is integer GB (1–100 globally; product-specific limits may narrow the range) and durations are explicitly 15/30/60/90 days.
- Quote formula is `base_price_rials + selected_gb × per_gb_rials`. An active `reseller` role gets 5% discount using exactly the same public rate; direct buyers pay full public rate. No float arithmetic. Zero percent is allowed by code config.
- Disabled products/rates cannot be quoted. Product rate edits affect future quotes; F09-C is responsible for immutable order snapshots.
- No orders, payments, wallet debit, provider API, Telegram purchase flow or subscription activation in F09-A.
- Run Pest, Larastan and Pint on PHP 8.4/8.5 before PR merge.

## F09-B acceptance criteria
- Logged-in active private-chat customer can open buying flow from Home or /buy. An empty catalog clearly shows unavailable rather than fake prices.
- When one product is active, buying opens directly to durations with **real** computed minimum-volume prices (1 GB globally, or narrower product minimum). Multiple products display safe paginated selection with starting prices.
- Valid duration shows preset volumes (1/10/30/50/100 where allowed, plus exact min/max), **each with current price**. A special button accepts integer custom 1–100 GB (or narrower bounds), including ASCII/Persian/Arabic digits, after a 10-minute per-actor opt-in.
- Quote preview shows actual public price, 5% role-based reseller discount where applicable and final price; re-evaluates price and role server-side. Fractional tomans round *up only for display*.
- Unauthorized, forged, inactive, expired or now-disabled selections cannot access sensitive data, mutate wallet or persist orders.
- No buy confirmation button, payment, orders, Remnawave API or migrations/new dependencies in F09-B. CI + live E2E acceptance are distinct.

## F09-C acceptance criteria
- A customer sees price before making an order; the explicit confirm button is bound to the user and a ten-minute preview and cannot be forged or used by another account.
- An order is only created if the active identity, product, duration, volume, public price and role-dependent discount are still valid and **exactly match the preview**; stale quotes require a new preview.
- A successful callback stores one price snapshot and `pending_payment` order; database-unique idempotency key prevents two orders on retry. A retry returns the same order even if the catalog rate later changes.
- Customer sees only their own orders (latest ten and individual detail). Snapshot never silently changes after operator modifies catalog prices.
- F09-C adds no balance debit, wallet reservation, payment confirmation, bank integration, subscriptions, Remnawave API or server/network code. Any future paid order transition must be implemented and verified separately.
- Tests cover ownership, duplicated callback, token expiry, stale quotes, role revocation, inactive buyer and zero Billing postings.
