# AI-01 / AI-02 — GapGPT foundation and Denix group chat

**Status (2026-11-09): AI-01, AI-02A and AI-02B merged (#425–#427); Deniz identity/knowledge update pending CI.** Two phases, three small independent PRs. Explicit operator approval is required to start each implementation scope. `master` auto-deploys to Production.

## Contract and design

- Reuse Laravel 13 Modular Monolith: `app/Modules/AI/Application` for use cases/model allowlist; `app/Interfaces/Telegram` for the separate Denix bot and Super Admin-only group presentation. No separate service or generic AI gateway.
- Use the official `laravel/ai` SDK with a named `openai-compatible` provider if its **installed** version and GapGPT response format pass verification. GapGPT documents OpenAI `chat.completions`, Bearer API key and `https://api.gapgpt.app/v1` (optional alternate: `https://api.gapapi.com/v1`). Verify the final SDK configuration and real request before activation.
- Initial *candidates*, not proven-live allowlist: `gpt-6-luna`, `gapgpt-deepseek-v4.1-flash`, `gpt-6.1-terra`, `gpt-6.1-sol`. Only enable IDs that return valid live text responses. No model-specific clients or automatic unverified model discovery.
- Secrets and infrastructure URL in deployment ENV; separate `DENAGATE_AI_ENABLED=false` global kill switch and trusted `DENAGATE_AI_GROUP_CHAT_ID`. Reject missing/invalid settings, group IDs and unknown models. Never put API keys, prompts or provider payloads in logs.
- Reuse existing Redis/queue and Identity Actions. No business SQL access, Provider tools, SSH, payment actions or user-specific account-data tools. Never give the model an executable or privileged capability.

No AI retry, no stored failed conversation turn, no new quota or worker. ### Deniz Telegram Business — Phase 2 (2026-11-09, approved)

- **Reused components:** exact Deniz bot token and isolated authenticated webhook, its single dedicated \`ai\` queue, \`AskAssistant\`, \`ModelCatalog\` and the bounded \`DenixConversationState\` (private positive-chat/actor identity never collides with the negative Super Admin group). No new bot, provider model, cache store, SQL customer conversation table or queue worker.
- **Two independent activation controls:** the existing Admin Bot Spatie \`deniz_business_support.enabled\` switch and a **new deployment kill switch** \`DENAGATE_AI_BUSINESS_REPLIES_ENABLED=false\` must both be ON along with the pre-existing global AI and Deniz bot switches. This deployment gate prevents a previously selected ON UI state from silently becoming live after source deployment. \`DENAGATE_AI_SUPPORT_BUSINESS_USER_ID\` must equal the verified numeric ID of the connected Business account. Default OFF; explicitly authorize deployment activation separately.
- **Webhook:** accept only authentic new, private, positive-ID incoming customer text with valid message ID/date, matching \`from.id == chat.id\`, \`from.is_bot == false\`, and no bot/outgoing marker; drop old/future timestamps, unsupported media, edits and deletions. A second replay fence handles identical Business \`message_id\` under a different \`update_id\`. Run synchronous fail-closed queue/cache configuration checks before enqueueing; never call GapGPT or send from the webhook.
- **Worker:** before provider inference and again before any send, call Telegram Bot API \`getBusinessConnection(business_connection_id)\`, verify exact connection ID, trusted owner, \`is_enabled=true\`, non-bot owner and \`rights.can_reply=true\`. Any missing, invalid, revoked, unconfigured or failed live lookup denies sending; never trust an old webhook cached connection as permission. The original customer message must be within the Telegram Business 24-hour reply window, with a small future-clock-skew allowance.
- **Delivery:** \`sendMessage\` must include the exact \`business_connection_id\`, private customer \`chat_id\` and reply-to message ID. No bot-DM fallback or tool actions. A single cache attempt key before the billable call prevents repeated inference or uncertain Telegram delivery on retries. \`tries=1\`, \`timeout=40\`, connection read timeouts 4s and send timeout 6s; keep existing independent worker \`--timeout=45\` and shared \`retry_after >45\`. Store history only after confirmed Telegram delivery; fallback on provider error is one generic nonbillable text reply with identical access checks, without leaking upstream exception bodies. First answer identifies Deniz as an AI assistant.
- **Limits and privacy:** independent 5 requests per customer per 10 minutes, 20 per customer per rolling day, 50 Business answers globally per rolling day, with at most one nonbillable quota notice per customer per hour. Model and prompt are existing verified defaults; no extra model or variable pricing. Short-lived 30-minute context / 30 messages / 6000 characters from the shared conversation-state rules, partitioned per private customer (positive Telegram ID), distinct from the manager group (negative Telegram ID). Logs only safe outcome/tokens/latency and exception types; never private text or Telegram identifiers.
- **Human handoff:** exact user requests «پشتیبان انسانی»، «اپراتور» or «صحبت با پشتیبان» get one no-model message and pause automatic answers in this private conversation for 24 hours in shared cache. Sending «شروع دنیز» explicitly resumes. Any manual outgoing support-account Business message additionally pauses that conversation for 24 hours, excluding echoes with \`sender_business_bot\`. Telegram's native manual per-chat pause remains available to the operator; this is not a claim of assignment, notification or a new ticket. No unconditional human reply guarantee.
- **CI gates:** mocked Telegram and GapGPT transport tests for switch OFF, strict customer intake, deduplication, quotas, live owner/rights, source/reply scope, second rights check, forced OFF during inference, context isolation, one-shot failure handling and handoff. These are **not** live Business/GapGPT acceptance. PHP 8.4 PR matrix, MySQL, PHPStan and Pint required before merging. PHP 8.5 runs on repository's scheduled matrix.
- **Production enablement (separate operator action):** verify numeric Business owner ID and actual connected rights, register the Deniz webhook for the four Business update types + existing \`message\` without dropping pending updates, verify root UI remains OFF and deployment gate OFF, then use one explicitly authorized test customer to toggle gate and root switch, check reply permission, chat delivery and rate limits, and verify operator pause and rollback. Keep BOTH switches OFF if live Business smoke cannot be completed.
- **Rollback:** turn either switch OFF; queued workers independently re-check both before buying or sending. Existing Admin/Sales/group bots remain unaffected. No schema migrations or new dependencies in Phase 2.
